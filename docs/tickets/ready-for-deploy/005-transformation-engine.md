## Request
Nikhil's larger goal: "Upload bond form + upload structured data → AI understands both → automatically maps fields → performs any required transformations → generates all completed bond forms. I want to get as close as possible to having zero manual configuration for a new bond form."

Three asks make it up: (1) no manual `<<tags>>` — the AI finds fields on an untagged form; (2) both `.docx` and `.pdf` untagged forms, original formatting preserved exactly; (3) the AI handles data *transformations*, not just direct copies (e.g. `$1,200,000` → "one million two hundred thousand and 00/100 dollars"; later date/currency/percent formatting, name/address formatting, combining several columns into one field, splitting one value across several fields).

Clarified in brainstorming: the same bond form is **reused across many Excel batches**, so a form is analysed once and the result saved as a reviewable **recipe** (see Roadmap of sub-projects below).

**This ticket covers sub-project 1 only: the transformation engine.** It is the format-independent, deterministic piece, and the only one that also delivers value on today's tagged flow.

## Sub-project roadmap (each gets its own spec → plan → build cycle)
1. **Transformation engine** — this ticket.
2. **Word field detection + write-back + recipe model.** Approach A: extract text with positions, LLM identifies label→blank pairs, plain code writes values. Word first because XML edits preserve formatting most easily.
3. **PDF field detection + write-back.** Hardest. Known limit: PDFs embed only font *subsets*, so new text cannot reuse the original font exactly — closest match is a visually similar font with the same size/colour. "Exact" typography is not achievable for PDF in general; say so rather than overclaim.
4. **Recipe storage + review UI.** Review UX proposed by Nikhil 2026-10-04: after uploading template + Excel the user sees "Analysing…", then the template opens; at every detected field an overlay shows the proposed fill text with Approve / Reject beside it — approve fills it and moves to the next field, reject skips straight to the next. Approved result is saved as the recipe. (Open design points, to settle in this sub-project's own brainstorm: what Reject means — leave blank vs pick another column; rendering Word documents for overlay, since Word fields are located in XML not page coordinates; which sample row the overlay shows.) Persistent storage decision deferred (Railway volume with JSON files vs Railway Postgres). Recipes hold no client data — only field locations, column mappings, and transform specs. Note this is *not* the in-memory-session storage Nikhil declined to change on 2026-08-25; recipes are reusable configuration that must survive restarts.

Detection approach chosen: **A (text + geometry → LLM)**. Not chosen now: vision LLM (imprecise coordinates, heavier privacy exposure, costlier); may be added later as a fallback for scanned PDFs, so detectors should return a common "field location" shape. Scanned PDFs are assumed not to be a large part of the workload — revisit if wrong.

## Design (approved)

### Shape
New pure module `backend/services/transforms.py`: takes a transform spec and one Excel row, returns the string to write. No knowledge of documents, FastAPI, or the LLM.

```
apply_transform({"type": "amount_in_words", "source": "Penal Sum"}, row)
  → "one million two hundred thousand and 00/100 dollars"
```

- **Catalog v1:** `copy` (today's behaviour), `amount_in_words`, `currency` (`$1,200,000.00`), `date_format` (target pattern), `join` (template like `"{First} {Last}"`).
- **Deferred (added later as catalog entries, each with own tests):** percent, split, name/address formatting.
- **Registry:** each transform is a registered function with validated params; unknown `type` is rejected.
- The LLM only ever **picks a transform and its parameters from the catalog** — it never writes conversion logic. A recipe can therefore only do things that are tested.

### Correctness rules
- **Money uses `Decimal`, never float.** Input may be `1200000`, `1200000.0`, or `"$1,200,000"` — all parse to the same value. (`excel_parser` stringifies every cell with `str(val)`, so numeric cells arrive as strings like `"1200000"` / `"1200000.0"`, and date cells as `"2024-01-15 00:00:00"`. The engine must accept those shapes.)
- **Never guess.** Blank, non-numeric or ambiguous input raises `TransformError`. In bulk generation that row becomes `status: "error"` and the other rows continue (existing TICKET-003 partial-success contract). A visible error beats a wrong amount on a bond.
- **Amount-in-words convention (confirmed by Nikhil: lowercase):** whole-dollar part lowercase, hyphenated tens-ones, no "and" inside the number, cents as a fraction over 100, then `dollars`.
  - `1200000` → `one million two hundred thousand and 00/100 dollars`
  - `1234.56` → `one thousand two hundred thirty-four and 56/100 dollars`
- **USD only** for now (Nikhil's reply "just numbers – dollar" was read as dollars only; if it meant a different wording, revisit before implementation).
- **Own implementation, no `num2words` dependency.** ~40 lines, fully test-covered; the library's quirks (commas, British "and" in "one hundred and one") would need post-processing, and exact wording on a legal amount should be fully controlled.

### Integration with the existing flow
- **API:** a mapping value stays a column-name string (today's behaviour) **or** may be a spec object. Old clients keep working unchanged. Touches `GenerateRequest.mapping` / `GenerateAllRequest.mapping` (currently `dict[str, str]`, `main.py` ~lines 70, 78) and `_build_fill_values` (~line 181).
- **LLM mapper (`llm_mapper.py`):** may propose a transform for a placeholder (e.g. `Penal Sum in Words`). Response is validated against the catalog; invalid types are dropped. This is the same mechanism later sub-projects reuse.
- **UI:** no frontend work in this ticket. Until sub-projects 2 and 4 land, the only way to see a transform is a tagged template whose placeholder name hints at one.

### Testing (TDD, failing test first)
- Table-driven unit tests per transform. Edge cases for `amount_in_words`: zero, cents, 1 vs 1,000, 1,000,000, 21/99 hyphenation, negative, blank, `"$1,200,000"`, `"1200000.0"`, text.
- API tests for the mixed mapping format (string value and spec value in one mapping), including a bulk run where one row's transform errors and the rest succeed.
- LLM-mapper tests: valid spec accepted, unknown type dropped, fallback behaviour unchanged when no LLM is available.

### Decisions needed from Nikhil before implementation (plan below assumes the **recommended** option for each; change the affected steps if a different option is picked)
- **D1 — Spec errors vs data errors.** Recommended: two exception classes. `TransformSpecError(TransformError)` = the spec itself is bad (unknown `type`, missing/extra params, `source` not a real Excel column, unsupported date pattern) → rejected **for the whole request with 400, before any row is filled**, in both `/api/generate` and `/api/generate-all` (a bad spec is a request bug, not a messy-row problem, so it should not produce N identical per-row errors). `TransformError` = this row's data can't be converted → `/api/generate` returns **400** with `detail` naming the placeholder; `/api/generate-all` marks that row `status: "error"` and continues (TICKET-003 contract).
- **D2 — Skip vs error for blank rows.** Today a bulk row is `skipped` when every filled value is blank. With transforms, a fully blank row would raise in `amount_in_words` and become an `error` instead, and `join` can produce non-blank separator text from blank inputs. Recommended: decide skip **on the raw source columns** the mapping references (all blank → `skipped`, transforms never run); otherwise blank input to a strict transform → `error`.
- **D3 — Which date inputs are accepted.** `excel_parser` turns real date cells into `"2024-01-15 00:00:00"`, but a date typed as text arrives verbatim (`"01/15/2024"`, `"15/01/2024"`, `"Jan 15, 2024"`). Recommended (per "never guess"): accept only ISO `YYYY-MM-DD` and `YYYY-MM-DD 00:00:00`; a non-midnight time component (`"2024-01-15 13:45:00"`) → `TransformError`; any slash/text date → `TransformError` (`03/04/2024` is genuinely ambiguous). Alternative: accept `MM/DD/YYYY` as US-only — say so explicitly if wanted.
- **D4 — `date_format` pattern language.** "Target pattern" is unspecified. Raw `strftime` is unsafe for an LLM-chosen param (arbitrary directives, locale-dependent `%B`, `%-d` is platform-specific and `%d` gives "January 05, 2024"). Recommended: a strftime-style **whitelist** — `%Y %y %m %-m %d %-d %B %b` plus literal text; anything else is a `TransformSpecError`. `%-d`/`%-m` are implemented in our own code (not passed to the C library) and month names come from a fixed English list, not the locale. Ordinal days ("15th day of January") deferred to a later catalog entry.
- **D5 — What `join` references and how blanks behave.** Recommended: `join` has **no `source`**; its only param is `template`, and every `{...}` token is an exact Excel column name (spaces allowed, e.g. `"{First Name} {Last Name}"`; `{{`/`}}` for literal braces). Parsed with our own regex, not `str.format` (column names containing `.`, `[`, `:` or `!` break `str.format`). Unknown column → `TransformSpecError`. Blank pieces are substituted as `""`, then whitespace runs are collapsed and the result stripped; if *all* referenced columns are blank the result is `""`. Known limitation to accept or reject: a template like `"{City}, {State}"` with blank City yields `", NY"` (dangling separator) — not cleaned up in v1.
- **D6 — Money input edge cases.** Recommended (strict): optional leading `$`, optional *correctly grouped* commas (`1,200,000` yes, `1,20,0000` no), up to any number of decimals **only if digits beyond the 2nd are zeros** (`1200000.0`, `1234.500` OK; `1234.567` → error). Negative, accounting-style `(1,200)`, scientific notation (`1e+16`, which `str(float)` emits for huge floats), and amounts ≥ 1,000,000,000,000,000 (one quadrillion) → `TransformError`. Note: a formula-computed Excel cell can arrive as `"1234.5600000000001"` (float artifact) — strict rule makes that an **error, not rounded**. Confirm that's preferred over rounding half-up to cents.
- **D7 — `/api/map` exposure before the UI exists (see risk R1).** The frontend types `mapping` as `Record<string, string>`; a spec object returned by `/api/map` would render as "not mapped" in the review dropdown while still being sent back and applied at generate time — the user would see one thing and get another on a real bond. Recommended: `map_fields(..., allow_transforms=False)` by default and `MapRequest.allow_transforms: bool = False`; the current frontend never sends it, so live behaviour is unchanged until a UI can display specs (sub-project 4). The parsing/validation of LLM-proposed specs is still built and tested in full here.
- **D8 — Singular "dollar".** Design says always `dollars`. `1` → `"one and 00/100 dollars"` (bank-check convention keeps the plural). Confirm.
- **D9 — Out-of-range `row_index` in `/api/generate`.** `get_row_data` returns `{}` for a row past the end; today that yields a blank document (pinned by `test_generate_with_out_of_range_row_index_produces_blank_fields`). Recommended: keep that test passing — `copy` and plain-string mappings stay lenient (missing/blank → `""`); a strict transform on `{}` raises `TransformError` → 400, which is arguably better than a blank bond. Confirm.

### Risks / pre-existing issues found while planning (not fixed by this plan — flagged for a decision)
- **R1 (frontend, ties to D7):** `frontend/src/app/page.tsx` stores `mapping` as `Record<string, string>` (line 64), renders `value={mapping[ph] || ""}` in the review `<select>` and `excelPreview[0][mapping[ph]]` as the preview. A spec object would display as unmapped / preview "—" but still be submitted. Hence the `allow_transforms=False` default.
- **R2 (PDF templates):** `fill_pdf` writes the value as a single `insert_text` line at the placeholder's position with no wrapping or box fitting. `amount_in_words` output (~60–100 chars) will run past the placeholder area on many PDF forms and can overlap other printed text. Word templates are unaffected (inline text). Not addressed here; worth a later ticket or an explicit "Word templates only for long transforms" note.
- **R3 (pre-existing bug, Word):** `fill_word_template` (`services/word_processor.py` line 48–49) inserts values into `document.xml` **without XML-escaping**. A cell containing `&` or `<` (e.g. `Smith & Sons LLC` — very plausible for a surety principal) produces a corrupt `.docx`. Exists today with plain copies; `join` makes it more likely. Recommend a separate bugfix ticket (failing test: fill a value with `&`, assert the output zip's XML parses).
- **R4:** float artifacts from formula cells (D6) will surface as row errors rather than silently rounded amounts — correct per "never guess", but may be noisy on real sheets; worth checking a real (local, uncommitted) client sheet's numeric columns before deciding.
