# Dindu (DocFiller)

## What it is
DocFiller automates filling document templates (PDF or Word) from a data source (Excel). Flow:

1. User uploads an Excel file (data source) + a template file (PDF or Word) containing placeholders — `<<Field Name>>` style for PDF, `MERGEFIELD`/`«FieldName»` style for Word.
2. Backend parses both: extracts Excel columns + preview rows, and extracts the template's placeholder names.
3. User (or the flow) asks the backend to map placeholders to Excel columns — an LLM does this semantically (e.g. "Applicant Name" → "Name"), so column naming doesn't need to match exactly.
4. Given a chosen Excel row and the mapping, the backend fills the template and returns the generated document.

## Status: real use, real documents
This is not experimental — real client documents (e.g. bond forms, financial paperwork) are processed here. That means:
- Document content is sent to a third-party LLM (OpenAI, or Gemini as fallback) for field mapping.
- Session data (uploaded file bytes, parsed data) is held in an **in-memory Python dict** on the server — not persisted to disk or a database, not encrypted at rest, cleared on server restart.
- Correctness of field mapping matters — a wrong mapping fills a real document incorrectly.

## Stack

**Backend** (`backend/`) — FastAPI, Python 3.11, deployed to Railway (`Procfile`, `nixpacks.toml`, `runtime.txt`), with LibreOffice installed for PDF conversion (see System dependencies below).
- `main.py` — API routes (see below)
- `services/excel_parser.py` — reads Excel (openpyxl), extracts columns/preview/rows
- `services/pdf_processor.py` — extracts `<<placeholder>>` fields from PDFs and fills them (pymupdf)
- `services/word_processor.py` — extracts MERGEFIELD fields from Word docs, fills them, and (on the PDF-conversion path only) flattens merge-field structure to prevent LibreOffice from re-rendering unfilled placeholders
- `services/format_converter.py` — converts filled Word documents to PDF via headless LibreOffice (`soffice --headless --convert-to pdf`) using batched processing with per-file retry (see TICKET-004 for design and justification)
- `services/llm_mapper.py` — maps placeholders → Excel columns via LLM. Tries OpenAI (`OPENAI_API_KEY`) first, falls back to Gemini (`GEMINI_API_KEY`) if unset/fails, falls back to fuzzy string matching if both are unavailable.

**System dependencies** (backend):
- LibreOffice (`libreoffice-writer` + `fonts-liberation` on Debian/Ubuntu) — installed in the Railway production container via `RAILPACK_DEPLOY_APT_PACKAGES` service variable. Installed at *deploy time* (not build time) so the binary is available when conversion requests arrive at runtime. Used for DOCX → PDF conversion only.

**Frontend** (`frontend/`) — Next.js 16.3.2, React 19.2.8, TypeScript, deployed to Vercel. A real single-page UI exists (`src/app/page.tsx` — upload → setup modal (naming column + format choice) → review mapping → generate flow; styling in `globals.css`), built directly rather than via ticket process, so it predates the `docs/tickets/` system. Vitest + React Testing Library test suite exists (`src/app/page.test.tsx`, landed with TICKET-003, extended by TICKET-004 — see `docs/TESTING.md`). Note: this Next.js version is new enough that it may differ from an LLM's training data; check `frontend/node_modules/next/dist/docs/` before writing Next.js-specific code (per `frontend/AGENTS.md`, auto-generated by `next dev` itself).

## API endpoints (backend)
- `GET /api/health` — health check; also reports `pdf_conversion: bool` (whether `soffice` is available on this server)
- `POST /api/upload` — accepts Excel + template files, returns session_id, excel columns/preview, template placeholders, and `template_type` (`"pdf"`/`"word"`)
- `POST /api/map` — given session_id + columns + placeholders, returns LLM-generated mapping
- `POST /api/generate` — given session_id + mapping + row index (+ optional `filename_column`, `output_format`), returns the filled document as a file download in the requested format (`"original"`/`"pdf"`/`"docx"`; a PDF template requesting `"docx"` is rejected with 400)
- `POST /api/generate-all` — given session_id + mapping (+ optional `filename_column`, `output_format`), fills every row in the sheet in one request and returns all documents inline as base64 (nothing retained server-side); capped at 200 rows (`MAX_BULK_ROWS`), returns partial success per row (`ok`/`error`/`skipped`) rather than failing the whole batch on one bad row — including a per-row PDF conversion failure

## Known limitations (intentional, for now)
- Sessions are in-memory only — won't survive a server restart or scale across multiple backend instances. Flagged in code as MVP-only (`main.py`). Deliberately not changing this — see `docs/DECISIONS.md`.
- PDF→DOCX conversion is out of scope (rejected as fragile/lossy for real documents) — only DOCX/DOCM→PDF is supported.
- `flatten_merge_fields` (the PDF-conversion correctness fix) only handles the classic Word MERGEFIELD field-code shape, not the less common `<w:fldSimple>` shorthand — see TICKET-004's QA review.
- No authentication/authorization on any endpoint.
