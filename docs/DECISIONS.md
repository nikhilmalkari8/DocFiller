# Decisions

Append-only log of significant decisions and why they were made. Never edit or delete past entries — if a decision changes, add a new entry that supersedes it and says so. This is what makes "how did we get here" reconstructible later.

### 2026-08-23 — Split deployment: FastAPI backend on Railway, Next.js frontend on Vercel
**Decision:** Backend and frontend deploy to separate platforms rather than a single combined deploy.
**Why:** Railway handles the Python/FastAPI runtime and system-level dependencies (pymupdf needs system libs) well via `nixpacks.toml`; Vercel is the natural fit for Next.js. A single `vercel.json` covering both was tried and removed in favor of this split (see commits `4c9d873`, `9c79092`, `210541f`).

### 2026-08-23 — In-memory session storage for MVP
**Decision:** Uploaded file data and parsed results are held in a plain Python dict (`sessions`) in `main.py`, keyed by a generated session ID.
**Why:** Fastest way to get the upload → map → generate flow working end-to-end without standing up a database or Redis. Explicitly called out in code as MVP-only.
**Known consequence:** Won't survive a server restart, won't work across multiple backend instances, no persistence or encryption at rest. Real documents pass through this. Tracked in `docs/ROADMAP.md` as future work, not urgent yet.

### 2026-08-23 — LLM provider fallback chain: OpenAI → Gemini → fuzzy string matching
**Decision:** `services/llm_mapper.py` tries OpenAI first (if `OPENAI_API_KEY` set), falls back to Gemini (if `GEMINI_API_KEY` set) on failure or absence, and falls back further to plain fuzzy/substring matching if neither LLM is available or both fail.
**Why:** Avoids a hard dependency on a single LLM provider being up or configured — the app degrades gracefully to basic matching rather than failing outright. Currently only `OPENAI_API_KEY` is actually set in `.env`; the Gemini path exists but is unexercised in practice right now.

### 2026-08-23 — CORS allowlist explicitly scoped, not wildcard-open
**Decision:** `main.py` CORS middleware lists specific allowed origins (localhost dev URLs + the specific deployed Vercel domain) rather than allowing all origins.
**Why:** Fixed after initially missing the deployed frontend's actual domain (commit `b9643a3`, "Fix CORS: allow Vercel frontend domain"). Needs updating any time a new frontend deployment URL is added.

### 2026-08-23 — Documentation system established: docs/ + per-feature tickets
**Decision:** Added `docs/PROJECT.md`, `docs/ROADMAP.md`, `docs/DECISIONS.md`, `docs/TESTING.md`, and a `docs/tickets/` folder tracking feature work through `pending/ → ready-for-deploy/ → completed/` states, one markdown file per ticket.
**Why:** Nikhil wants every project session to be able to reconstruct project history and current state without re-deriving it from scratch, and wants each feature's request/plan/implementation/tests/impact documented as a permanent artifact rather than lost in chat history. `completed` requires the change to actually be deployed, not just tested — `ready-for-deploy` is the intermediate state for tested-but-not-yet-shipped work, since deployment is always confirmed with Nikhil explicitly rather than done autonomously.

### 2026-08-23 — Single `qa-reviewer` subagent instead of a multi-role team (architect/senior/junior/manager)
**Decision:** Added one custom subagent, `.claude/agents/qa-reviewer.md`, scoped to this project. It does an independent fresh-eyes review pass (correctness, test quality, data-handling risk, scope discipline) after implementation, as part of the "verify" step in the TDD workflow — it reports findings only, doesn't fix them.
**Why:** Nikhil considered setting up a full virtual org chart of subagents (architect, senior engineer, junior engineers, QA, manager) to drive TDD. Rejected: Claude Code subagents are stateless per invocation — a "senior engineer" agent has no memory of being that role last time, so a role hierarchy mostly adds coordination overhead and per-feature cost without adding real capability, since the underlying model is identical regardless of the label. What's genuinely useful is a reviewer with fresh eyes and no attachment to the implementation (a real, well-supported pattern — same idea as the `code-review` skill), so that's the one piece that got built.

### 2026-08-23 — Plan/review tooling routed by task size: custom agents for routine work, superpowers plan/subagent tooling for large decomposable work
**Decision:** For a normal single-coherent-change ticket, use the `planner` agent (global, `~/.claude/agents/planner.md`) for the plan step and `qa-reviewer` (project-local) for the verify step. Reserve the superpowers `writing-plans` skill and `subagent-driven-development` workflow (fresh subagent per task, each with an explicit `Interfaces: Consumes/Produces` contract, executed in isolated worktrees) for genuinely large, decomposable work with independent parallelizable pieces. Documented in `CLAUDE.md` under the feature/bugfix workflow.
**Why:** Compared both pairs directly. `planner` already writes straight into `docs/tickets/pending/NNN-slug.md` in the ticket template's own `Step → verify` format — it was built to match this project's conventions. `qa-reviewer` is pre-loaded with Dindu-specific risk knowledge (real financial documents, silent-wrong-mapping as the worst failure mode, in-memory session constraints, exact test commands) that a generic reviewer would need re-explained on every dispatch. `writing-plans` is a heavier apparatus by design — file-structure decomposition and inter-task contracts meant to let independent subagents implement tasks with zero shared context — and saves plans to `docs/superpowers/plans/`, a different location/format than `docs/tickets/`; defaulting to it on routine tickets would fragment the ticket system rather than add value. The superpowers tooling earns its overhead only when a task is actually large enough to split across parallel, non-overlapping subagent work (e.g. the eventual real frontend build).

### 2026-08-23 — `planner` dispatch made mandatory: Opus plans, Sonnet (session default) implements
**Decision:** The orchestrating session stays on the default model (Sonnet); the `planner` agent (pinned `model: opus` in its own frontmatter) must always be dispatched for the plan/research step on real code work, never skipped in favor of the orchestrating session doing that research and planning itself — even when the session has already read the relevant files and dispatching feels redundant.
**Why:** On ticket 001 (backend test suite), the orchestrating session explored the codebase and wrote the plan itself instead of dispatching `planner`, reasoning that it had already done equivalent research during brainstorming and a fresh dispatch would be redundant. Nikhil caught this: the point of `planner` isn't just producing a plan document, it's that planning/architecture happens at Opus tier specifically, while everything else (implementation, doc updates, git operations, routine conversation) runs on the cheaper default model. Skipping the dispatch defeats that split regardless of whether the resulting plan would have looked identical. The session's own general guidance ("don't spawn agents unless asked, handle it inline — spawning re-derives context and is the expensive path") is what actually pushed toward skipping it; that default is correct for avoiding pointless dispatch overhead, but doesn't apply here since this dispatch isn't pointless — it's the entire mechanism for the model-tiering architecture. Considered running the whole orchestrating session on Opus instead (removing the extra dispatch hop entirely); rejected as less cost-efficient for no real effectiveness gain, since the bulk of a session's volume is conversation, file reads, test runs, and doc bookkeeping — none of which are reasoning-bottlenecked enough to need Opus, unlike the planning decision itself.

### 2026-08-24 — Railway backend had no zero-downtime deploys and rebuilt on every push, causing a real "Load failed" upload error
**Bug report:** Nikhil uploaded a real `.xlsm` Excel file and `.docm` Word template on the live site and got a red "Load failed" error banner on clicking "Upload & Analyze."
**Investigation (systematic-debugging, root cause before any fix):** re-sent the exact same file-type combination directly to the live backend — it succeeded cleanly (`200`, correct CORS header, valid session), ruling out a code bug in `.xlsm`/`.docm` handling or the CORS allowlist. Checked Railway's deployment history instead: the backend had been redeployed **6 times within about an hour**, once for *every* git push to `main` that session — including pure documentation commits that never touched `backend/` at all. `get-service-config` confirmed no `watchPatterns` were set (Railway rebuilds on any push to the whole monorepo) and no `healthcheckPath` was configured, meaning each redeploy likely did a hard cutover (old container killed, new one started) rather than a health-gated rolling deploy. "Load failed" is literally the string WebKit/Safari's `fetch()` throws for a raw network-level failure (no HTTP response at all) — not the app's own `"Upload failed"` JSON-error fallback text — which matches a request landing in one of those restart gaps rather than a real validation failure.
**Root cause:** unscoped Railway auto-redeploys (triggered by any push, not just backend changes) combined with no health-check-gated zero-downtime rollover, creating brief but real availability gaps that a live upload could land in.
**Fix:** `mcp__railway__update-service` with `watchPatterns: ["backend/**"]` (stop redeploying on frontend/docs-only pushes) and `healthcheckPath: "/api/health"` (Railway already has this endpoint; gates traffic cutover on the new container actually responding healthy, so deploys that *do* still happen become zero-downtime).
**Verification:** triggered a real redeploy after applying the fix and polled `/api/health` every 2 seconds for the full ~95-second redeploy window — `200` continuously, zero gaps. Confirmed via `list-deployments` that the new deployment reached `SUCCESS` and the old one was only marked `REMOVED` 3 seconds *after* — a genuine health-gated cutover, not a coincidence. The `watchPatterns` half of the fix is applied and expected to work (Railway's documented behavior), but wasn't independently re-verified with a live doc-only push in this session — noted rather than overclaimed.

### 2026-08-25 — TICKET-003: bulk generation, inline base64, client-side zip, Vitest lands here
**Bulk generation returns everything inline, nothing retained server-side.** `POST /api/generate-all` fills every row in one synchronous request and returns all documents as base64 in the JSON response — no follow-up download endpoint, nothing added to the `sessions` dict. Deliberately avoids depending on session durability between a generate call and a later download click, since `.claude/rules/in-memory-sessions.md` already establishes that assumption doesn't hold (a Railway restart/redeploy happens on every push to `main`). Capped at `MAX_BULK_ROWS = 200`, failing loudly with a 400 rather than risking a gateway timeout on a huge synchronous request. Partial success is a first-class outcome — one bad row's exception is caught per-row and reported as `status: "error"` without blocking the other rows, since real client sheets are messy and losing N-1 good documents over one bad row is worse than showing N-1 downloads plus one visible error.
**Filenames come from a user-chosen Excel column, not a row number.** New `backend/services/filenames.py::build_filenames` — sanitizes illegal filesystem characters, truncates to 60 chars, falls back to `row_{n}` when the column is blank or unset, and appends `_row_{n}` to every colliding name so a zip of same-named documents never silently overwrites entries (a real data-loss risk once "Download All" exists). The same `filename_column` is optional on single-row `/api/generate` too, so naming stays consistent between the two entry points.
**Client-side zip via `jszip`, not a server-side zip endpoint.** The alternative would re-fill every row a second time purely to package them (the backend never retains filled bytes), or would require retaining them just for zipping — exactly what the stateless design above avoids. Since the bytes are already in the browser after generation, zipping there is free. Approved as a new ~100KB frontend runtime dependency.
**Vitest + React Testing Library lands here** — the first ticket to change real frontend component behavior (a setup modal with conditional flow, plus a results list), so the interim `node:test` token harness from TICKET-002 (which existed only because a CSS-token swap has no logic to test) is no longer sufficient and the deferred setup was due. Scoped to `frontend/src/app/page.test.tsx` only — the setup modal and bulk flow, not a retroactive pass over the rest of `page.tsx`. Config had to be scoped to `include: ['src/**/*.test.{ts,tsx}']` since Vitest's default file discovery collided with the separate `test:tokens` harness in `frontend/tests/`. RTL needs an explicit `afterEach(cleanup)` — Vitest doesn't auto-cleanup between tests the way Jest does, which surfaced as "multiple elements found" failures across every test after the first until fixed.
**Scope changed mid-planning.** Nikhil messaged the `planner` subagent directly while it was running with a materially different design (a setup modal for naming + format, chosen upfront, plus "Download All" as a zip) than the plan's first pass (no modal, per-document downloads only, no zip). The `planner` incorporated this and additionally recommended keeping the Format half of the modal as a static, non-functional line in this ticket and deferring the real selector to TICKET-004 — isolating the LibreOffice/Railway build risk from this ticket's actual ask, so a failed format-conversion deploy can't take down bulk generation with it. That static line is known to be factually wrong for a Word template until TICKET-004 lands (it always says "PDF — same as your template"); acceptable because both tickets are being implemented in the same session, so it's never actually shipped to a real user in that state.

### 2026-08-25 — TICKET-004: PDF conversion via LibreOffice, flatten-before-convert, format chosen once up front, batched with per-file retry
**PDF conversion engine: headless LibreOffice (`soffice --headless --convert-to pdf`) subprocess, not a pure-Python library or a cloud API.** `docx2pdf`-style libraries are thin wrappers around the same system dependency (Word/LibreOffice) — they'd hide it, work locally (Word is installed on this machine), and fail on Railway's Linux container, the worst possible failure shape. Genuinely pure-Python paths (HTML/WeasyPrint, reportlab) re-implement Word layout from scratch and lose tables/columns/positioning — unacceptable for bond forms and financial paperwork where the filled document is the deliverable. Third-party cloud conversion APIs were rejected specifically on data-handling grounds: this project already sends column/placeholder names and preview values to OpenAI/Gemini for mapping, but a conversion API would receive the **complete filled client document** — a materially bigger exposure, for a feature LibreOffice can do entirely inside the existing Railway container. New `backend/services/format_converter.py` is pure sync bytes-in/bytes-out with no FastAPI/asyncio knowledge, so a later swap to a Gotenberg sidecar service (considered, not chosen — doubles the deployable services for one feature) stays a one-file change.
**Flatten merge fields before converting — mitigates a silent-unfilled-PDF hazard.** `fill_word_template` replaces only a MERGEFIELD's cached *display text*, deliberately leaving the underlying field-code structure (`fldChar begin`/`instrText`/`fldChar separate`/`fldChar end`) intact, since Word renders the cached value and that's why the existing DOCX download already works. LibreOffice, however, imports `MERGEFIELD` as a database field and — with no data source attached — can re-render it from the raw field instruction instead, silently printing `«Name»` (or blank) in the PDF instead of the filled value. New `flatten_merge_fields()` in `word_processor.py` strips that structure to literal text, applied **only on the PDF-conversion path** so the Word download's bytes are completely unchanged. Verified for real (not just via mocks): two unmocked tests in `test_format_converter.py` fill a real DOCX, flatten, convert, and assert the extracted PDF text contains the real value and neither `«Name»` nor `MERGEFIELD`.
**Format is chosen once, in the setup modal, before generation — not per download afterward.** Superseded an earlier per-download-format design (see the TICKET-003 entry above, where the modal's Format line shipped as a static placeholder specifically to leave room for this). Nothing filled is ever retained server-side regardless of format — bytes are streamed (single) or returned inline as base64 (bulk) and dropped immediately; choosing format up front just means exactly one artifact is ever produced per document, never both, so a batch of N documents never pays LibreOffice's ~1–3s warm / ~5–10s cold / ~150–300MB-RSS cost twice for one that's only downloaded once.
**Bulk conversion is batched (one `soffice` invocation per request, not one per row) with per-file retry, plus a process-wide `asyncio.Semaphore(1)`.** Batching amortizes soffice's per-invocation startup cost across all rows in a bulk request. The tradeoff is failure isolation — one bad document could otherwise take the whole batch's conversions down with it, which would violate TICKET-003's "one bad row must not block the others" contract. Mitigated: after a batch run, any input whose output PDF is missing (including one whose invocation raised `subprocess.TimeoutExpired` — see the QA-found bug below) is retried individually; only if that retry also fails does that one row become `status: "error"`. The semaphore serializes all conversions process-wide since this API has no auth and two overlapping bulk PDF requests could otherwise run multiple ~150–300MB LibreOffice processes concurrently on a small Railway container.
**Installed via a Railway service environment variable, not `nixpacks.toml` — this service actually builds with Railpack.** Confirmed via `mcp__railway__get-service-config` (`"build":{"builder":"RAILPACK"}`) that `backend/nixpacks.toml`, despite existing in the repo, is very likely dead config the real build never reads. Railpack's actual mechanism for installing system apt packages is two service environment variables: `RAILPACK_BUILD_APT_PACKAGES` (build-time only) and `RAILPACK_DEPLOY_APT_PACKAGES` (installed into the final runtime image). Since `soffice` needs to exist when a conversion request arrives at runtime — not just during the build — `RAILPACK_DEPLOY_APT_PACKAGES=libreoffice-writer fonts-liberation` was set directly as a Railway service variable via `mcp__railway__set-variables`. Verified empirically (not just documented) by triggering a real Railway build and grepping the build logs for successful `libreoffice-writer`/`fonts-liberation` installation. `nixpacks.toml` is left in the repo untouched — harmless, but not the mechanism doing anything here.
**QA review found and fixed two real bugs** (full detail in the ticket's own QA review section, `docs/tickets/ready-for-deploy/004-format-choice-download.md`): (1) clicking "Skip" in the setup modal cleared `filenameColumn`, which also happened to be the same state gating the Review step's only other path back into the modal — so the new Format selector became permanently unreachable for the rest of the session after a Skip, not just the naming choice it was originally gating. Fixed by making that Review-step row unconditional. (2) `format_converter._run_batch`'s `subprocess.run(..., timeout=timeout)` call had no exception handling around it — a single hung/pathological document's `TimeoutExpired` propagated raw out of `convert_many_to_pdf`, capable of aborting an entire `/api/generate-all` bulk request and losing every row that had already filled and converted successfully, despite the per-file retry design above existing specifically to prevent one bad document from taking the batch down. Fixed by catching the timeout and routing it into the same missing-output retry path as a clean soffice failure.
**Accepted, not fixed:** `flatten_merge_fields`'s regex targets the classic Word MERGEFIELD field-code shape this app's own `word_processor.py` produces (and what real Word mail-merge templates use) — it does not handle the less common `<w:fldSimple>` shorthand some other document-generation tools emit for the same field type. If a real client template ever used that shape, the exact silent-unfilled-PDF hazard this ticket exists to close could resurface for that one document. No fixture in the test suite constructs it. Accepted on the same basis as excluding PDF→DOCX conversion entirely: out of scope until shown to matter for a real template this app actually receives.
